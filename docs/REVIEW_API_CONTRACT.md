# Guest Review API Contract, Version 1.1

The API reads `web/api/_review_manifest.json`, a minimal projection generated from `web/data/manifest.json`. This file stores the source file's SHA-256 and only the fields needed to validate reviews and record provenance. After changing the source manifest, run `python scripts/build_review_contract.py --write` and include the generated contract in the same change. `python scripts/build_review_contract.py --check` and the readiness report detect a missing or out-of-sync contract. This contract does not replace the public manifest or validate scientific results.

GET/POST add `session_scope`, a hash label that cannot replace the cookie for authentication. The frontend uses it to distinguish a lost old session from a snapshot belonging to the same session. Losing the cookie does not automatically delete unexpired local notes; they remain separately archived, even if the new session has a review with the same analysis/scene/selection, and are not uploaded again automatically. An old cloud record without a scope is reattached only if its review ID matches the current session; if this cannot be verified, the local copy stays separate. GET refreshes a valid cookie for the active session. LocalStorage also limits records to 180 days from their save date; an invalid or past expiry is not renewed automatically.

If a cloud review is edited and POST fails, the local draft retains `review_id`, `cloud_scope`, `cloud_expires_at`, and `cloud_pending` so the prior server copy is not forgotten. The draft's local expiry and the actual cloud expiry are separate; a local save does not renew the cloud record. If POST was sent but its response was lost, `cloud_pending` also means the server record *may* have been written; the result is unknown. When deleting, the frontend checks scope with GET and sends DELETE using the old ID or key only if the session still matches. If the session changed, it deletes only the local copy and reports that the old server record could not be deleted. An unsent draft remains separately archived when the session changes.

A GET snapshot is ignored if a mutation starts or finishes during the request, or while a mutation is still running. The user's in-progress edits are retained in memory instead of being overwritten by the snapshot; unsaved text is not persisted across reload until the user saves it. Mutations for the same key are blocked from running concurrently in one tab. Cloud scope, ID, and expiry are retained in JSON export to distinguish drafts, cloud records, and archives.

The GET scope check and DELETE/POST are separate requests; the cookie may change between them, and idempotent API DELETE does not confirm that a record exists. Concurrent tabs/devices also have no version or transaction protection against overwrites; this mechanism does not guarantee synchronization or atomic deletion. If the session or server cannot be verified, the frontend keeps the local copy and asks the user to retry.

`/api/reviews` is for personal notes in the demo; a review is a user's opinion, not confirmation of an astronomical detection. GET creates a random `__Host-spherex-review` session cookie when needed, with Secure, HttpOnly, SameSite=Strict, and a 180-day expiry. The cookie is the only credential; losing or deleting it means the review cannot be recovered. Do not use this API as an account or review-sharing system.

- `GET` returns `storage: "mongodb"`, `contract_version: "1.1"`, and `reviews` (up to 100 unexpired records). Each review retains the v1 fields and adds `review_id` (64-character hex, stable for the session and key) and `expires_at` (ISO 8601 UTC). Expired records are not returned even if MongoDB TTL has not physically deleted them.
- `POST` requires JSON with `scene_id`, `selection`, `status` (`uncertain`, `interesting`, or `artifact`), the current `analysis_sha256`, and optional `note` (up to 2,000 characters and UTF-8 encodable). The server establishes provenance from the manifest and does not trust client-supplied provenance fields. Saving the same key updates it and renews its 180-day expiry. The response retains `saved`, `storage`, and v1 `review`, and adds version, ID, and expiry. A stale analysis hash or lone surrogate is rejected with 400 before storage access.
- `DELETE` accepts `{"review_id": "..."}` or a v1 payload with `scene_id`, `selection`, and `analysis_sha256` (64-character hex hash), even if the manifest has changed or the scene no longer exists. It searches/deletes only within the current session. The idempotent response `{"deleted": true}` does not reveal whether the record existed or belonged to another session. IDs are derived for older records too; no backfill is required. Deleting by ID scans the current session's keys and therefore costs more as the number of records awaiting TTL cleanup grows.
- POST and DELETE require an HTTPS `Origin` exactly matching `Host`, plus the session cookie; JSON body `Content-Length` must be 1–8,192 bytes. GET does not require Origin. The API returns `405` with `Allow` for common unsupported methods; `400` for invalid JSON/fields; `401` for a missing session; `403` for an invalid Origin; `409 review_limit` when the session owner already has 100 unexpired reviews and the request would add/revive one; `409 storage_limit` when 20,000 physical review documents already exist and the request would add a document; `411`, `413`, or `415` for body errors; `429` for rate limiting; and `503` when storage/transactions are unavailable. An uncertain commit returns `503 save_outcome_unknown`: the operation **may have been saved**, so the client must check with GET before retrying. Errors do not return stack traces.
- Limits are 90 requests/minute per bucket based on the first address in `X-Forwarded-For`, plus 60 valid POSTs/minute globally (including updates; GET/DELETE do not consume the POST quota). `RateLimit-Limit`, `RateLimit-Remaining`, and `RateLimit-Reset` describe the IP bucket, not the global POST quota; `429` includes `Retry-After`. A deployment should trust the IP header only if the edge proxy controls and overwrites it; without a header, requests share the `unknown` bucket. This is basic load reduction, not strong abuse prevention.
- The 20,000 limit counts expired documents until TTL deletes them; updates to an unexpired document remain allowed at the limit. Reviving an expired document must satisfy the owner's 100-unexpired-review limit. Existing data and IDs are not changed; old records are not deleted to meet quota. This is a document-count limit and does not guarantee remaining Atlas storage in bytes.
- Each valid POST uses a transaction to write a shared `review_guard` document, then checks the count and upserts in the same session. Write conflicts are retried with a limit; all MongoDB operations in a request have a 10-second client budget. If transactions are unavailable or retries are exhausted, the request fails closed; GET and DELETE do not depend on transactions. The quota design applies only when **all** review writers use this guard; old instances, direct database writes, or mixed-version deployments can exceed the limit. The shared document is a bottleneck, and counting up to 20,000 documents has a cost; there is no M0 benchmark or load-test evidence.
- Each handler response has a random `X-Request-ID`. JSON logs include request ID, normalized method, status, error group, and processing time; they do not include note, cookie, MongoDB URI, or raw IP. No dedicated alerting/monitoring system is included.

The v1 payload and smoke script remain compatible. The interface now stores `review_id` from GET/POST and supports deleting old-analysis reviews from history; the server still accepts a v1 payload containing the three old key fields. A local archive scoped to a session cannot restore server access after its cookie is lost.
