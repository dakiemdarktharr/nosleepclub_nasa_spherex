# Review API: bounded load baseline

This preregistered exercise is a single modest baseline, not an availability SLO, throughput ceiling, attack-volume test, failover test, or backup/restore test. It targets only `https://nosleepclub-nasa-spherex.vercel.app` at API commit `80324933bfab21a73a0a2e3f05c447b99f2a81d2`. No alternate target, production database URI, or credentials are accepted. The public manifest is fetched once and must match the Git blob at that commit; its strict scene and analysis hash supply the test input.

After reviewing the source, tests and this protocol, run `python scripts/verify_review_load.py --design` and commit those three files plus `docs/evidence/0.10/review-load-design.json` before any live run. The runner checks the design against the current bytes and Git HEAD before touching the network. Do not amend or rerun an unfavorable baseline as if it were the same result. Every run receives a new timestamp and nonce and writes an exclusive, ignored receipt in `data/raw/benchmark/`; retain failures. One invocation has no resume or retries.

Twelve independent fresh sessions run in four groups of three. Each group starts five waves: GET an empty snapshot and cookie; POST a unique random disposable note; GET exact same-owner readback and stable ID; DELETE that ID; GET an empty snapshot. Each wave starts at least six seconds after the previous wave completes, and has at most three in flight. This gives at most 0.5 requests/second averaged over wave spacing, no more than three simultaneous QA notes and 12 POSTs. The expected successful run has 60 API calls across approximately 114 seconds plus request time; timeout is 5 seconds connect and 20 seconds read. Redirects are forbidden, TLS verification is enabled, sessions ignore environment proxies, and the total API request cap is 84 including cleanup. The initial manifest request is additional.

Each API response is checked against the fixed commit; GET/POST check the storage contract and owner scope, and readback checks the exact generated note and stable ID. An initially nonempty snapshot or repeated scope immediately stops new work and that session is never written or deleted. Two unexpected HTTP/transport failures stop new work; a semantic contract, scope or commit violation stops it immediately. A request already in the same wave may finish. No failed or cold attempt is excluded or retried for the latency statistic.

After any interrupted lifecycle, cleanup is separately tagged. Only an initially empty, uniquely scoped session that attempted its own POST may be inspected. A timeout may have committed, so cleanup GETs the session and deletes only a row whose complete generated QA content matches; it then verifies empty. Unknown or foreign rows are never deleted. If a matching owner/scope/commit or cleanup cannot be verified, cleanup remains unverified and the receipt must not claim success. Keep the receipt and escalate manual follow-up without exposing cookies or notes.

The gate requires all 60 planned requests to return HTTP 200 and satisfy lifecycle, contract and commit checks; all 12 touched owners must be verified empty; nearest-rank p95 across every planned GET attempt must be at most 3 seconds, and p95 for POST and DELETE separately and combined must each be at most 5 seconds. Failed attempts and timeouts remain in the raw records and percentile samples. Cleanup attempts are reported separately. Status, latency, safe request ID and categorical errors are retained; response bodies, notes, raw scopes, review IDs, cookies and secret-bearing exception strings are never recorded. A pass applies only to this short observation and does not close the wider security, load or operational recovery criteria.
