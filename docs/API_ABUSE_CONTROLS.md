# Public API Request Limits

`/api/observations` and `/api/frame` check limits **after validating parameters and before querying IRSA**. These quotas are proposed for an initial demo; they are not an SLO or evidence of DDoS protection.

| Endpoint | Per IP/minute | All IPs/minute |
| --- | ---: | ---: |
| observations | 12 | 60 |
| frame | 8 | 24 |

Each process also has a burst filter that allows at most eight requests from the same IP and endpoint within a one-second window, before writing to MongoDB. State is thread-locked, capped at 4,096 keys, and evicts old keys when full. Fixed second/minute windows can allow bursts around window boundaries. Memory belongs to one process and is not shared across instances or cold starts; this is **not a distributed quota**. When the filter blocks a request, the API returns 429, `Retry-After` in seconds, `Cache-Control: no-store`, and `X-Request-ID`. The guard/API logs do not include raw IPs, URLs, coordinates, or notes.

When `MONGODB_URI` is configured, instances use the existing database’s `api_limits` collection. Each counter is incremented atomically with `find_one_and_update`; the key is a SHA-256 hash of the environment namespace, endpoint, minute, and hashed scope/IP. A TTL index on `expires_at` removes a bucket after about 1–2 minutes. TTL expiry is asynchronous cleanup; quota uses the new minute key and does not wait for TTL. Hashing an IP is pseudonymization, **not strong anonymization**: there is no secret salt, and an address may be recovered by dictionary search. This limited data is used only to reduce abuse, not as a user identity. The original IP is not written to the collection.

The global counter increments before the per-IP counter. Each increment is atomic, but the two increments are not a transaction. A request denied by the IP limit, or a failure between the steps, may still consume global quota; this is a conservative choice. Once the global limit is reached, new requests do not create additional IP documents for that minute. TTL and global limits bound the number of documents in a bucket but do not eliminate writes to the global counter. Endpoints and environments use separate buckets; review quotas are not combined here.

With `VERCEL_ENV=production`, only one valid IP address in `X-Forwarded-For` is accepted. A missing header or invalid IP string returns 503 `rate_identity_unavailable`. [Vercel documents this header as the client IP and says the platform overwrites it to prevent spoofing](https://vercel.com/docs/headers/request-headers). This relies on the request actually passing through Vercel. A proxy in front may cause the proxy IP to be counted for multiple users, and Trusted Proxy Enterprise changes that assumption. Verify the request path and header on the deployment before release; the header alone is not evidence of encryption. If the URI is missing, MongoDB cannot be reached or written to, or the TTL index cannot be created, production fails closed with 503 `rate_storage_unavailable`, does not call IRSA, and does not expose connection details.

Preview/local environments do not trust the forwarded header and use `client_address`. Without MongoDB, they use a thread-locked in-memory counter with at most 8,192 keys; exceeding the limit returns 503. This fallback only protects each process and does not enforce a global quota across instances. If preview has a URI, it still uses MongoDB but with a namespace separate from production. Behind a proxy, `client_address` may represent the proxy rather than the client. Preview experiments are not evidence of production rate limiting.

Successful `frame` responses may be cached by the browser/CDN for 300 seconds; a cached request may not reach the guard. These limits protect origin processing and upstream queries, not every cache hit. They do not protect against botnets/DDoS, instance bursts, or quota consumption from many IPs. Edge controls and quota/latency monitoring are needed before broad public use. IP quotas may be shared by users behind NAT, and the global quota can be exhausted. No load test, real MongoDB test, Vercel deployment verification, or alerting service had been completed at this checkpoint.

Tests use a thread-locked fake collection and an HTTP handler with a mocked upstream. They check concurrent limits, isolation between endpoints, fail-closed behavior, TTL, burst filtering, 429 responses, and that raw IPs are not stored. No new service was added and no credentials or cloud configuration were changed.

Hardening after review: a missing or unrecognized deployment context returns 503 `deployment_context_unavailable`. The local fallback requires `SPHEREX_LOCAL_API=1`, which the loopback launcher sets explicitly; this flag does not override `VERCEL_ENV=production`. System environment variables must be exposed correctly in Vercel; a missing variable is not treated as local. Checks include missing `VERCEL_ENV`/`VERCEL` and a local flag mistakenly set in production.

The review API has separate quotas: 90 requests per IP per minute and 60 valid POSTs globally per minute, plus limits of 100 active records per owner and 20,000 physical documents overall. A transaction writes to the shared `review_guard` before checking and upserting to prevent write skew among POSTs. GET/DELETE do not need a transaction; TTL removes expired documents asynchronously. These are demo proposals, not proof of DDoS resistance or sufficient byte capacity. Counting the full collection and contention on a shared write can be slow or increase conflicts; POST fails closed on errors or exhausted retries. Older versions or writers outside the API can violate the invariant. See the [review API contract](REVIEW_API_CONTRACT.md) for error details and `save_outcome_unknown`.

MongoDB describes a [Free cluster as a three-node replica set running MongoDB 8.0](https://www.mongodb.com/docs/atlas/reference/free-shared-limitations/) and [transactions as supported on replica sets](https://www.mongodb.com/docs/manual/core/transactions-production-consideration/). This does not replace checking the actual cluster and permissions. Tests in `tests/test_review_transactions.py` run only when a disposable loopback replica set is configured. No real MongoDB result or Atlas benchmark was available at this checkpoint. FakeDB does not prove isolation or limits under real concurrency.
