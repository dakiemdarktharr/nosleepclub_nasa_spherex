# Operations and Pre-Release Checks

Current scope is an exploratory viewing tool, not confirmation of an astronomical detection. The [ledger](PRODUCTION_READINESS.md) tracks 20 items; **green CI does not establish scientific accuracy, production security, load capacity, or data recovery**. The published 0.9 result did not pass the overall/covariance gate; `point_passed=true` means the baseline was compared with itself. Do not promote or market this result as a scientific finding.

## Before each release

1. Record commit, clean/dirty state, environment, deployment ID, and manifest/protocol hashes; compare deployed commit with the checked version. `python scripts/check_readiness.py` emits JSON with Git state, configuration/dependency/hash checks, ledger, and 0.9 evidence. It does not run tests. By default it exits 0 only if its repository checks pass; `--require-science` currently always returns nonzero because there is no independent science-verification mechanism. This is fail-closed behavior, not scientific approval when document status changes.
2. On Windows, run `.venv/Scripts/python.exe -m unittest discover -s tests -v`; elsewhere, run `python -m unittest discover -s tests -v` in an environment with `requirements.txt` and `web/requirements.txt` installed. Review skipped tests separately; raw FITS are not stored in the repository, so tests using raw data may skip in CI. `.github/workflows/checks.yml` runs all Python tests, compilation/source whitespace checks, JavaScript syntax, and ReviewStore cases with Node 24 LTS. It uses GitHub `contents: read`, does not deploy or expose secrets to the job; artifact `python-readiness-<commit>` contains only `readiness.json` and `unittest.log` and is retained for seven days. The workflow must run on GitHub and be configured as a required check in repository settings before it can serve as a gate; a workflow file alone does not enable branch protection.
3. Review [review contract](REVIEW_API_CONTRACT.md), [observations](OBSERVATION_API_CONTRACT.md), [frame](FRAME_API_CONTRACT.md), especially IRSA timeouts, quotas, release differences, and scientific limits. Check CSP, functions with the appropriate 15/30/120-second `maxDuration`, and package size in the real environment; CI does not prove the provider accepts those limits.

## Rollback and observation

Before release, record the previous deployment and checked commit/hash. If rollback is required, route traffic back to a known-working deployment using the project's Vercel mechanism, then check URL/deployment ID, manifest hash, and read-only smoke paths before recording results. Code rollback does not restore MongoDB; do not restore a database to production during investigation. If schema changed, check compatibility before switching traffic. This document does not claim a rollback drill has been completed.

APIs emit structured logs with request ID, status, error group, and latency; logs are not intended to include cookies, notes, MongoDB URI, raw IP, or coordinates. Use request IDs to correlate events within access controls, check whether the platform independently records sensitive query strings/headers, and set retention according to an operator-approved policy. Public-frame cache may return request ID and retrieval timestamp for the cached response. Do not collect review contents for analytics.

Helper `_telemetry.py` adds an allowlist for log fields, severity by status (2xx/3xx info to stdout, 4xx warning and 5xx error to stderr), frame error codes, and IRSA HTTP status when present. It does not log upstream URL/body. [Production check at fc17f96](evidence/0.10/telemetry-fc17f96.json) confirms a 200 request has JSON `level:info`, while a 504 has JSON `level:error` on stderr, **but Vercel still assigns platform level `info` to this 504 line**. Error filters must parse application JSON `status/level`; selecting only platform errors would miss an observed failure. Do not infer error rates from line counts: deduplicate with application request ID because each request may have both platform and application events. The verifier retains valid JSON error codes in failed receipts without copying response bodies.

Monitor request counts, 4xx/5xx error rates and timeouts by endpoint/category, p50/p95/p99 latency, cache-hit rate if available, MongoDB storage, and function use/timeouts. Distinguish missing telemetry from healthy service. There is no measured SLO/error budget: before configuring alerts, collect a real workload baseline, choose observation window and availability/latency objectives with an owner, test notifications, and record the receiving channel. Current timeout values are configuration limits, not SLO measurements. No load-test evidence exists; only test IRSA at an authorized scope/frequency and stop if errors/load rise.

## MongoDB backup and restore drill

The [synthetic backup/restore primitive](BACKUP_RESTORE_PROTOCOL.md) uses Fernet/BSON and is restricted to a loopback fixture with two separate UUID prefixes. It has no production CLI or route. Encryption unit tests do not replace the two real-replica-set tests; CI must install `requirements-ops.txt` (separate from the web bundle). Production destination, key custody, retention, deletion journal, and RPO/RTO have not been verified.

Do not assume M0 has free automatic backups. Current [MongoDB Free Cluster Backups documentation](https://www.mongodb.com/docs/atlas/backup/cloud-backup/free-cluster-backup/) describes M0 snapshot backup as an optional paid private preview requiring a payment method; overview pages may differ by version/deployment. Check tier, region, backup status, cost, and availability at the time of operations; **do not enable a paid service automatically**. If no verified backup exists, record the review-loss risk. Guest reviews have a 180-day TTL and contain private data; copies also require encryption, access controls, and an appropriate deletion period.

To plan a non-destructive drill, the operator must prepare existing least-privilege access, controlled encrypted storage, and a **separate sandbox database** capable of restore. If permissions or environment are missing, stop and record the blocker; do not expand permissions casually. Use MongoDB Database Tools as described in [mongodump](https://www.mongodb.com/docs/database-tools/mongodump/) and [mongorestore](https://www.mongodb.com/docs/database-tools/mongorestore/) with protected URI/secret configuration; do not put URI/password in command line, logs, or CI artifacts. Export only the review database and record tool version, time, and archive hash; restore only to the sandbox using separate target configuration, then check namespaces, indexes, TTL, unexpired record counts, and a test review read/delete. Do not copy the restored data to production or modify existing collections during the drill. Remove temporary copies under the approved policy, verify permissions, and record backup/restore times to measure actual RPO/RTO. This document is not evidence that a backup or restore has occurred.
