# SPHEREx Photometric Convention Audit: Evidence and Limits

This audit reads only code, official documentation, and calibration headers. It does not fit images, inject sources, or change the locked pipeline. Public snapshots inspected are R6.4 commit `d31bc5a6666b4530c6e233c2484c586b4a598b24` and R6.5.5 commit `aa0ba446ee12971024fe13dc1c47387615bbe85e`. These snapshots do not establish the exact contents of the internal build that generated each QR2 product.

## Units and solid angle

[IRSA](https://caltech-ipac.github.io/spherex-archive-documentation/spherex-data-products/) describes IMAGE as surface brightness in MJy/sr and SAPM as solid angle per pixel in arcsec². For a pixel with the correct Ω and position:

`flux_pixel[Jy] = IMAGE_pixel[MJy/sr] × 10^6 × Ω_pixel[sr]`.

This converts the integrated flux density in a pixel; it does not isolate a source's total flux from background, neighbors, or bandpass. For a units-only example, if Ω = (6.15 arcsec)², then Ω = 8.889963240650299×10⁻¹⁰ sr and 1 MJy/sr × Ω = 888.996324065 µJy. This is **illustrative** and does not replace the actual SAPM map. The [IRSA tutorial](https://caltech-ipac.github.io/irsa-tutorials/spherex-source-discovery-tool-demo/) demonstrates converting each IMAGE pixel with SAPM for that detector pixel.

Tractor code uses a different choice at a later post-fit step. In [R6.4](https://github.com/Caltech-IPAC/spherex-pipelines/blob/d31bc5a6666b4530c6e233c2484c586b4a598b24/py_src/spx_utils/photometry/tractor_utils.py#L363-L389) and [R6.5.5](https://github.com/Caltech-IPAC/spherex-pipelines/blob/aa0ba446ee12971024fe13dc1c47387615bbe85e/py_src/spx_utils/photometry/tractor_utils.py#L363-L389), `MJysr_to_uJy` multiplies the MJy/sr amplitude by SAPM **at the pixel nearest the source position**, with an `oversample²` divisor. [R6.4 forced photometry](https://github.com/Caltech-IPAC/spherex-pipelines/blob/d31bc5a6666b4530c6e233c2484c586b4a598b24/py_src/spx_tasks/perform_forced_photometry.py#L630-L638) and [R6.5.5](https://github.com/Caltech-IPAC/spherex-pipelines/blob/aa0ba446ee12971024fe13dc1c47387615bbe85e/py_src/spx_tasks/perform_forced_photometry.py#L649-L657) pass oversample=1. The fit amplitude is in image units with a native PSF normalized to 1; the catalog result is in µJy. This is the SAPM-at-center convention in the public code snapshot. It does not prove that pixelwise Ω is constant across the footprint or that an arbitrary cutout maps correctly to the full detector.

Read bytes 0–65535 of the [official example QR2 D6 SAPM](https://irsa.ipac.caltech.edu/ibe/data/spherex/qr2/solid_angle_pixel_map/cal-sapm-v2-2025-164/6/solid_angle_pixel_map_D6_spx_cal-sapm-v2-2025-164.fits) through HTTP 206: IMAGE records `ARRAY=6`, `DETCOORD=sky`, `BUNIT=arcsec2`, and dimensions 2040×2040. SHA-256 of the **byte range only**, not the whole FITS, is `b153300308d25ec8ac1196a394f1fd5e7d316e812a3759db7e92a57b7785a705`. [SAPM-generation code](https://github.com/Caltech-IPAC/spherex-pipelines/blob/d31bc5a6666b4530c6e233c2484c586b4a598b24/py_src/spx_tasks/update_field_distortion.py#L448-L454) assigns arcsec² units and sky orientation; Tractor reads `pix_map[y,x]`. This confirms only the example product and snapshot; it **does not bind the correct SAPM version to all 31 WISE images**. For a cutout, verify header, detector, provenance, and mapping from WCS A to active integer coordinates first; do not add an X flip just because it is D6. Do not infer another HDU's orientation from the SAPM rule. HISTORY in the currently opened 31 WISE files has no SAPM UUID, so the example file cannot be assigned to them as the correct calibration from this evidence. In particular, the R7 channel map has `DETCOORD=sky` while HDU BC/BW have `DETCOORD=DEVICE`; verify orientation per HDU and release.

## Gain and PSF templates

[R6.4 calibration application](https://github.com/Caltech-IPAC/spherex-pipelines/blob/d31bc5a6666b4530c6e233c2484c586b4a598b24/py_src/spx_tasks/apply_dark_flat_field_and_photo_calib.py#L157-L176) subtracts dark and multiplies by an array-valued gain with units `(MJy/sr)/(electron/s)`; variance is converted to squared units. Since IMAGE is already calibrated, do not apply gain again when converting IMAGE to Jy. Gain in a source-shot-noise model is a separate issue that needs the exact file/units and its own protocol.

[Tractor R6.4](https://github.com/Caltech-IPAC/spherex-pipelines/blob/d31bc5a6666b4530c6e233c2484c586b4a598b24/py_src/spx_utils/photometry/tractor_utils.py#L164-L222) shifts an oversampled PSF, downsamples with `INTER_AREA`, and normalizes the native patch to sum to 1; fitting uses `LinearPhotoCal(1)` with amplitude in image units. This describes PSF handling in that snapshot; it does not establish that the same operation is correct for QR3 ePSFs. The [IRSA ePSF tutorial](https://caltech-ipac.github.io/irsa-tutorials/spherex-psf/) says to shift, downsample, and normalize, while its specific code example calls `ImagePSF.evaluate` at native-pixel centers and divides by the stamp sum. Do not infer from the prose that a second pixel integration is needed for an ePSF that already includes pixel response. PSF type, LSF, interpolation, phase, and encircled energy must be specified before use.

Local `motion_analysis.py` multiplies the raw ePSF by `oversampling²/sum` before spline interpolation and samples at pixel centers; `continuous_epsf_model.py` keeps the same raw normalization and zero-pads. These operations **do not prove** that native ePSF sums equal 1 at every phase or that local amplitude is Jy. The local ePSF is a QR3 D6 product, header version `7.0.0b6.post2+g6b3a1a7`, SHA-256 `52f85faeb93d67ed2020b68a628fc947c1f0b78cbf9282ca193ec6d588ac1a36`, used with QR2 images; release differences require separate evaluation.

If a native template `p_i` is **proven** to be the source-flux fraction with a sum of 1 over a prespecified support, these two conditional formulae can guide study design:

* Under Tractor's point-source SAPM-at-center convention, `I_i[MJy/sr] = F[Jy] × p_i / (10^6 Ω_source[sr])`.
* Under pixel-by-pixel solid-angle conversion, `I_i[MJy/sr] = F[Jy] × p_i / (10^6 Ω_i[sr])`.

The formulae use different assumptions; neither has been compared or selected for WISE fitting. Do not renormalize over **only the unmasked pixels**, because that changes the flux meaning as a function of mask. Declare support, PSF flux outside the stamp, and its uncertainty. If response varies across the footprint, a scalar color factor per frame may be insufficient. Photon injection must also keep physical expected source counts nonnegative, use the correct gain, and avoid adding sky/read noise twice.

The new primitive `scripts/native_flux_template.py` implements only the Tractor center convention above: a 33×33 ePSF is zero-padded by 16 oversampled samples, cubic-splined, sampled over the full finite native lattice including positions outside the image, and normalized independently at each phase before applying the mask. It requires caller-provided Ω with units and provenance; it does not read SAPM, WCS, or image data. Degenerate sums are rejected, including cases where only floating-point roundoff remains on the full lattice. Negative pixel values from wings or the spline are retained; do not force the centroid or clip to zero. This normalization defines only a finite model support; it does not restore missing ePSF flux or prove the real ePSF. A template with negative values is not a valid Poisson expectation for injection; that requires a separate, nonnegative, physically validated source model.

## Spectral references and color correction

The [Explanatory Supplement v1.3](https://irsa.ipac.caltech.edu/data/SPHEREx/docs/SPHEREx_Expsupp_QR.pdf) describes QR2 absolute calibration based on 11 CALSPEC stars, predicting stellar spectra through each position's bandpass and applying zodiacal color correction. [R6.4/R6.5.5 code](https://github.com/Caltech-IPAC/spherex-pipelines/blob/d31bc5a6666b4530c6e233c2484c586b4a598b24/py_src/spx_tasks/update_photometric_calibration.py#L117-L148) computes the discrete mean `sum(trans × spectrum)/sum(trans)` and the zodiacal-to-stellar bandpass ratio after normalizing each spectrum at the sample nearest the observed wavelength. `trans` comes from `SPinst.Tabular_Bandpass`; its measurement definition, grid, units, and photon weighting have not been verified here. The supplement presents the zodiacal coefficient as an integral of normalized zodiacal spectrum; the code adds a stellar-spectrum denominator. Do not treat the expressions as equivalent without verifying definitions and remaining steps.

An important limitation: [R6.4 snapshot](https://github.com/Caltech-IPAC/spherex-pipelines/blob/d31bc5a6666b4530c6e233c2484c586b4a598b24/py_src/spx_tasks/estimate_abs_gain_matrix.py#L1507-L1516) accepts `photo_calib`, but the shown gain construction uses `ones / ArrayCalValues` and divides by `ff_est`. This is insufficient to reconstruct how the actual QR2 gain file was generated by the earlier internal build; it also does not refute the released calibration description in the supplement. There is no evidence here to choose flat Fν or flat νFν as the default reference spectrum, or to claim that the local diagnostic convention `R(λ)/λ` is SPHEREx calibration. PRISM/G395M, the R7 lab response, and QR2 gain are not yet linked into an absolute forward model.

Before a linked-flux fit, separately verify: the correct SAPM version and orientation per exposure; native ePSF and subpixel sums over fixed support; spectral response/calibration convention and source color ratio in consistent units; pixel-dependent response; covariance; and independent controls. Unit conversion alone is supported; the absolute source coefficient is not yet ready to publish or use as scientific truth. Source-code provenance and the status of each conclusion are listed in [photometric-convention.json](../web/data/external/photometric-convention.json).
